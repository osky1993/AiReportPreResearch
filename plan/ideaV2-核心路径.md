# 智能报告生成系统：核心路径（ideaV2 精简版）

> 本文是 `ideaV2.md` 的精简提取版。V2 全文 = 一条主线 + 一大圈保障体系（血缘、评测、灰度、归因分级、合规框架……）。本文只保留主线，用于团队对齐与 MVP 立项；保障体系作为后置加固项在文末列出。

## 一、一句话版本

> **锁口径（人）→ 结构化取数（现有引擎）→ 程序造事实 → LLM 只照着事实写 → 程序核数字 → 人签发。**

## 二、核心路径：一条 6 步流水线

```mermaid
flowchart LR
    U["用户需求"] --> S1["① 大纲确认<br/>HITL"]
    S1 --> S2["② 语义解析"]
    S2 --> S3["③ 安全取数<br/>NL2MQL2SQL"]
    S3 --> S4["④ 事实构建<br/>程序生成 FactRecord"]
    S4 --> S5["⑤ 章节撰写<br/>LLM 智能节点"]
    S5 --> S6["⑥ 证据审计<br/>程序核对数字"]
    S6 --> P["审批发布<br/>HITL"]
```

### ① 需求 → 大纲，人工确认口径

LLM 从自然语言需求中抽取报告类型、时间范围、指标清单，套用固定模板生成章节大纲，业务人员确认。

**这是第一个、也是最重要的人工卡点——口径在这里锁死，后面全是机器活。**

### ② 语义解析

把每个章节所需数据翻译成结构化查询规约：`metric_id + 维度 + 时间 + 过滤`（即 `MetricQuerySpec`）。

映射不唯一时停下来问人，**不猜**。

### ③ 安全取数

走已经业务验证过的 NL2MQL2SQL 引擎，只读凭证执行，留存 SQL 与结果哈希。

**这一步是现成的，不用新做。**

### ④ 事实构建

由程序（不是 LLM）把查询结果转成 `FactRecord`——带值、单位、周期、来源引用的最小事实单元。同比、环比等基础计算也在这一步做成 fact。

### ⑤ 章节撰写

LLM 只拿到事实对象写文字，不接触原始数据。**每个数字必须引用某个 fact。** 章节少时，撰写与全局编辑合并为一次 LLM 调用。

### ⑥ 证据审计 + 发布

程序逐一核对文中数字与所引 fact 是否一致，通过后人工审批发布。

**报告数字一致率是唯一的发布硬门禁。**

## 三、支撑路径只需要三样东西

| 资产 | MVP 范围 | 不需要做的 |
| --- | --- | --- |
| 报告模板 | **1 个**（章节树 + 每章推荐指标） | 模板库平台 |
| 指标语义定义 | **10～20 个**（公式、维度、权限） | 完整语义层平台 |
| 数据契约 | **2 个**：`MetricQuerySpec`、`FactRecord` | `ClaimRecord` 可先不要——"数字必须来自 fact"这一条审计规则就够了 |

契约示例（沿用 V2 定义）：

```yaml
MetricQuerySpec:
  spec_id: qs_001
  metric_id: deployment_success_rate
  dimensions: [team]
  period: 2026-W26
  comparison: week_over_week
  filters: []

FactRecord:
  fact_id: fact_001
  metric_id: deployment_success_rate
  value: 97.2
  unit: percent
  period: 2026-W26
  dimensions: {team: platform}
  sql_hash: sha256:...
  quality_status: passed
```

## 四、必须保留的两条底线

1. **失败关闭**：指标歧义、权限不足、数据质量失败、证据不充分时，停止并转人工，不猜测补全。
2. **最小运行状态**：每次运行有 `report_run_id`，各步骤输入输出落库，支持断点恢复和人工审批等待。不需要复杂状态机，但不能没有状态。

## 五、整体后置的部分（V2 原文对应章节）

| 后置项 | V2 出处 | 后置理由 |
| --- | --- | --- |
| 分层归因模型 + 事件知识库 + 异常分析 | §四.5、§五步骤 6 | V2 自己也声明阶段 1 不含归因；MVP 只出"发生了什么"，不解释"为什么" |
| 全局编辑独立节点 | §五步骤 8 | 章节少时并入撰写节点 |
| OpenLineage/OTel 血缘协议化 | §九 | `report_run_id` + 输入输出落库已够定位问题 |
| 影子运行、灰度发布、回归流水线 | §八.3 | 单场景 MVP 无版本并存需求 |
| 完整评测体系 | §八 | 黄金数据集从 100 条缩到 20～30 条真实需求，只测两个数：**取数结果等价率、报告数字一致率** |
| 多模板、多业务域、外部交付 | §十二阶段 3 | 内部单场景跑稳后再扩 |

## 六、MVP 落地顺序

1. 选定一个内部周报场景，冻结范围；
2. 定义 1 个模板 + 10～20 个指标语义 + 2 个数据契约；
3. 用 20～30 条真实需求测出现有 NL2MQL2SQL 的结果等价率基线；
4. 按 6 步流水线实现最小可信闭环；
5. 用「数字一致率 100%」作为发布硬门禁，跑通后再考虑第五节的加固项。
