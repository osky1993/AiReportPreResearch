# LLM Prompt 过载与边际效用验证实验方案

> 文档版本：v1.0  
> 编制日期：2026-08-03  
> 实验性质：独立验证性实验  
> 适用范围：面向业务方直观呈现 Prompt 约束增加后的收益、稳定性与过载风险  
> 边界说明：本实验与现有智能问数、智能报告功能相互独立，不接入其数据、流程或评测机制。

## 1. 实验目的

本实验不预设“Prompt 越长越差”，也不试图证明所有大模型都存在相同的固定字数上限，而是验证一个可观察、可重复、可证伪的业务命题：

> 在输入数据、任务目标、模型版本和生成参数保持一致时，随着 Prompt 中有效约束数量、交织程度和冲突密度增加，继续追加要求是否仍能稳定换来可交付价值；其边际收益从何处开始递减，又从何处开始影响核心指令遵循、事实正确性和跨次稳定性。

实验重点回答以下问题：

1. 从简洁 Prompt 增加到合理约束 Prompt，是否能够显著提高输出质量？
2. 当大量新增要求只是修辞、句式和格式微操时，质量增量是否开始低于 Prompt 编写与维护成本？
3. 当约束高度密集、相互交织时，模型是否开始“顾此失彼”，遗漏原有核心指令？
4. 输出退化究竟来自 Prompt 长度、约束数量、复杂依赖，还是逻辑冲突？
5. 对当前模型、当前任务而言，哪个区间具有最优的投入产出比？

## 2. 结论边界与诚信原则

本实验只能对以下范围负责：

- 指定模型及其指定版本；
- 指定数据分析场景；
- 指定 Prompt 构造方式；
- 指定 Temperature、Top-p、最大输出长度等运行参数；
- 实验发生时的供应商服务环境。

实验不得直接外推为“所有模型在 5000 字时都会崩溃”。约 300 字、800 字、2500 字和 5000 字只是便于业务理解的初始剂量点，正式分析必须记录模型 tokenizer 计算的实际 token 数。

正式执行遵循以下原则：

- “黄金区”“递减区”“过载区”“崩溃区”是实验结果，不是预先写入的组名；
- 即使 D 组表现最好，也必须原样披露；
- 即使现场某一次输出非常好或非常差，也不能替代完整重复样本；
- 不得挑选最符合预期的样本作为“代表结果”；
- 如果没有观察到过载，应明确得出“当前实验尚未触及边界”。

## 3. 实验场景

### 3.1 统一任务

根据一份冻结的“某地区近六个季度财政支出数据”，生成一篇 700—900 字的季度财政支出分析简报。

报告需要覆盖：

- 总体支出规模及变化方向；
- 主要支出分类及结构变化；
- 预算执行情况；
- 地区或部门差异；
- 值得关注的异常与风险；
- 基于现有事实能够支持的工作建议。

### 3.2 冻结数据包

建议准备 6 个季度、8 个支出分类，共约 48 条明细记录，至少包含：

- 财政支出总额；
- 同比、环比；
- 预算数、执行数、预算执行率；
- 教育、社会保障和就业、卫生健康、城乡建设等分类支出；
- 各地区或部门的分类数据；
- 分类占比和排名；
- 1—2 个明确标记的缺失值；
- 若干数值接近但期间、单位或口径不同的字段；
- 若干正负变化方向容易混淆的字段。

所有可核验事实均分配唯一 `fact_id`。实验前由业务人员和数据核验人员共同形成 12—15 个标准事实，包括：

- 总额及变化方向；
- 最大增量项、最大降幅项；
- 前三位支出分类；
- 预算执行率最高、最低项；
- 结构占比变化；
- 缺失数据不可推断项；
- 不允许升级为因果关系的相关性信息。

为了只测试 Prompt 承载能力，同比、环比、占比、排名等派生指标应预先计算后随数据提供，不要求模型自行计算，避免将算术能力引入主实验变量。

### 3.3 四组共同任务内核

以下内容在 A、B、C、D 四组中必须逐字保持一致：

- 只能使用给定数据和事实；
- 不得联网，不得引用外部背景；
- 不得擅自补全缺失值；
- 每个数据结论必须引用对应 `fact_id`；
- 不得把相关性自动表述为因果关系；
- 输出目标、篇幅和结构化返回格式一致；
- 数据正文、字段顺序和单位完全一致。

建议统一采用便于程序检查的 JSON 输出外壳，再将正文渲染给业务方阅读：

```json
{
  "title": "报告标题",
  "summary": "总体摘要",
  "sections": [
    {
      "name": "总体情况",
      "content": "正文",
      "evidence": ["fact_001", "fact_002"]
    }
  ]
}
```

## 4. 可证伪假设

### H1：合理约束收益

B 相比 A，在事实正确性和共享核心指令不劣化的前提下，结构、格式和业务可用性获得实质提升。

### H2：边际收益递减

从 B 增加到 C 后，Prompt token 和维护成本明显增加，但业务质量、一次可用率或人工修改时间的改善显著缩小。

### H3：过载损失

C 或 D 相比 B，不仅开始遗漏新增微观要求，而且四组共有的核心指令遵循度、事实正确性或稳定合格率出现超过业务容忍阈值的下降。

### H4：稳定性下降

C、D 的跨次波动高于 B，同一个 Prompt 多次生成时，遗漏规则、结构形态、语气和关键结论出现更明显的跳变。

### H5：冲突效应不同于长度效应

如果只有包含冲突的 D-Conflict 下降，而等长、无冲突的 D-Clean 保持稳定，则主要问题是指令冲突治理，不能解释为单纯的 Prompt 长度或模型容量问题。

## 5. 四阶主实验设计

正式盲评时仅使用 P、Q、R、S 等随机代码，评分锁定后再揭晓 A、B、C、D。

| 组别 | Prompt 构成 | 建议规模 | 代表状态 | 检验目的 |
|---|---|---:|---|---|
| A：基线组 | 角色、事实边界、核心分析维度、统一输出格式 | 约 300 字，5—7 条原子约束 | 最低充分指令 | 建立核心能力与自然输出基线 |
| B：合理约束组 | A＋标准政务结构、证据引用、重点排序、3 条明确格式规则 | 约 800 字，10—12 条原子约束 | 高价值约束区 | 检验合理约束能否提高一次可用率 |
| C：微操密集组 | B＋15—20 条禁用词、句式、段落、语气、标题等微观要求 | 约 2500 字，25—30 条原子约束 | 边际递减候选区 | 检验新增微操的兑现率及其对核心任务的影响 |
| D：极限负载组 | C＋跨章节依赖、例外规则、优先级和更多细碎要求 | 约 5000 字，50—60 条原子约束 | 高负载压力区 | 检验密集但可满足的要求是否导致核心退化或波动放大 |

四组采用严格嵌套设计：

```text
Prompt A = 固定任务内核 K
Prompt B = K + 高价值约束 H
Prompt C = K + H + 微操约束 M
Prompt D = K + H + M + 高负载约束 L
```

进入下一组后，前一组已有文字不得改写、删减或重新组织。新增内容只允许追加，避免“Prompt 写法被顺手优化”成为额外变量。

### 5.1 A 组约束示例

- 你是财政支出分析人员；
- 仅依据给定数据分析；
- 覆盖总体规模、结构、趋势和风险四个维度；
- 不得编造原因；
- 按统一 JSON 格式输出。

### 5.2 B 组新增约束示例

- 按“总体情况—结构变化—重点问题—工作建议”组织；
- 重要结论按业务影响排序；
- 每个数据结论必须列出 `fact_id`；
- 风险与建议必须分别呈现；
- 语言正式、客观、克制；
- 标题和章节名称使用统一格式。

### 5.3 C 组新增约束示例

- 摘要控制在指定字符区间；
- 每段首句不超过指定字数；
- 每章限制段落数量；
- 禁止使用一组常见套话；
- 指定某些句式、连接词或段尾表达；
- 标题字数、标点、列表样式固定；
- 建议必须以指定动词开头；
- 风险段落必须以指定短语结尾；
- 同一词语不得重复超过指定次数。

C 组要求应全部逻辑可满足，并尽可能做到程序可检测。

### 5.4 D 组新增约束示例

- 引入跨章节引用和前后呼应要求；
- 引入“满足条件 X 时使用格式 Y，否则使用格式 Z”的分支规则；
- 引入多层例外和优先级；
- 要求同一事实在不同章节采用不同表达方式；
- 对段落、句子、用词、标点和证据排列施加更密集限制；
- 增加互相竞争但仍可同时满足的目标，例如“极简表达”与“覆盖多个分析维度”。

D 主组仍需保证逻辑上可完成。真正不可同时满足的冲突只放入独立的 D-Conflict 诊断组。

## 6. 必要的后台诊断对照

### 6.1 D-Clean 与 D-Conflict

- **D-Clean**：长度、原子规则数和组合深度与 D 基本一致，所有规则逻辑兼容；
- **D-Conflict**：在总 token 数和规则数基本不变的前提下，替换其中 3—5 组要求为生产中常见的隐含冲突。

冲突示例：

- “每段不超过两句”与“每段分别用一句写现状、原因、风险、建议”；
- “禁止使用括号”与“所有口径必须在括号中说明”；
- “只输出正文”与“正文前必须提供独立摘要”；
- “全文禁用‘增长’”与“所有正向变化必须使用‘增长’表述”。

判读规则：

- 只有 D-Conflict 下降：主要是指令冲突问题；
- D-Clean 和 D-Conflict 都下降：存在更强的高复杂度过载证据；
- D-Conflict 中如果没有规定优先级，合理行为应包括识别冲突并请求澄清，不能把满足任意一边都简单判为失败。

### 6.2 B-Pad 长度对照

在 B 的有效约束不变的情况下，追加不包含新任务要求的中性参考文本，使其 token 数接近 C 或 D。

判读规则：

- B-Pad 稳定而 C/D 下降：问题主要来自约束数量、结构或竞争；
- B-Pad 也下降：原始长度、信息位置或注意分配可能是重要因素；
- B-Pad 只用于诊断，不能将无关填充文本作为生产 Prompt 优化手段。

## 7. 复杂度记录

不能只记录“中文字符数”。每个 Prompt 版本至少记录：

- 输入 token 数；
- Prompt 占上下文窗口的比例；
- 可验证原子约束总数；
- 共享核心约束数；
- 新增约束数；
- 禁止项数量；
- 条件分支数量；
- 跨段或跨章节依赖数量；
- 最大嵌套深度；
- 例外规则数量；
- 冲突指令对数；
- Prompt 文件哈希。

如果所有 Prompt 加最大输出长度仍远低于模型上下文窗口，则实验结果应表述为“高密度指令竞争或组织复杂度导致的退化”，而不是“上下文窗口耗尽”。

## 8. 固定变量

除 Prompt 指令块外，以下条件完全一致：

- 模型名称、精确版本或系统指纹；
- API 端点、区域和响应模式；
- Temperature；
- Top-p；
- 最大输出 token；
- 推理强度或同类模型参数；
- 停止条件；
- 系统消息；
- 数据正文及数据位置；
- 输出目标、篇幅和 JSON 格式；
- 工具、联网和检索权限；
- 会话历史；
- API 缓存策略；
- 数据快照和评分规则版本。

即使 Temperature 为 0，也不能把单次生成视为完全确定的结果。

## 9. 样本量、随机化与执行方式

### 9.1 单场景业务演示

推荐每组独立生成 30 次：

```text
4 个主组 × 30 次 = 120 次调用
```

如果同时执行 D-Clean、D-Conflict：

```text
5 个条件 × 30 次 = 150 次调用
```

建议分成两个独立批次，每批 15 次，确认结果可以复现。

### 9.2 更强的泛化验证

如果希望把结论从“当前数据快照”扩展到“财政支出分析任务族”，建议准备至少 8—12 个等难度数据包，每个条件重复 10 次以上。正式样本量可在试点后根据实际方差进行功效分析，目标检验功效不低于 80%。

### 9.3 配对与随机化

如果 API 支持 seed：

- 预先锁定 30 个 seed；
- A、B、C、D 使用相同 seed 集合；
- 每个“数据包 × seed”构成一个匹配区组。

如果 API 不支持 seed：

- 采用独立调用；
- 在短时间窗口内随机交错运行各组；
- 不允许先跑完 A 再跑 B、C、D；
- 记录调用时间、模型系统指纹和请求 ID。

每次调用必须：

- 使用全新会话；
- 不携带历史上下文；
- 不做自动重试、反思、修复或人工补写；
- 首次输出解析失败直接计入失败；
- 完整保留原始请求和原始响应。

## 10. 评分体系

### 10.1 原子指令清单

实验前将所有要求拆成原子指令，每条记录：

| 字段 | 说明 |
|---|---|
| `rule_id` | 唯一编号 |
| `rule_text` | 原始规则文本 |
| `level` | P0/P1/P2/P3 |
| `shared` | 是否为 A—D 共享核心规则 |
| `introduced_in` | 首次出现于 A/B/C/D 哪一层 |
| `weight` | 预先确定的业务权重 |
| `check_type` | 程序检查/人工检查 |
| `pass_rule` | 满足判据 |
| `conflict_with` | 是否与其他规则存在冲突 |

建议分级：

- **P0：事实硬门禁**——数值、期间、单位、方向、字段映射、不得编造；
- **P1：核心业务要求**——必要分析维度、证据、逻辑和关键结构；
- **P2：格式与表达要求**——章节、列表、标题、篇幅；
- **P3：修辞微观偏好**——句式、禁用词、语调、特定套话。

P0 错误不得被更好的文风或格式分数抵消。

### 10.2 事实硬门禁

自动检查并由专业核验人员复核：

- 数值是否正确；
- 期间是否正确；
- 单位是否正确；
- 正负方向是否正确；
- 字段是否错位；
- 是否擅自补全缺失数据；
- 是否存在无 `fact_id` 支撑的事实；
- 是否产生数据无法支持的因果结论。

任何 P0 错误均判定该次输出“不可直接交付”。

### 10.3 共享核心指令遵循度

只计算 A—D 四组共有的核心规则，用于公平判断新增要求是否开始挤压核心任务：

```text
CoreScore = 100 × Σ(规则权重 × 是否通过) / Σ规则权重
```

加权结果与未加权结果应同时披露，避免权重设置掩盖问题。

### 10.4 新增指令遵循度

```text
ExtraAdherence = 本层新增且被满足的规则数 / 本层新增规则总数
```

同时报告：

- **SSR（单指令满足率）**：所有原子指令中被满足的比例；
- **HSR（整份全通过率）**：一次输出是否满足该组全部指令。

不能只展示 HSR。即使每条指令相互独立且成功率恒为 95%，15 条全部满足的概率也只有约 46.3%，30 条全部满足的概率约为 21.5%。只有 SSR、共享核心遵循度、事实正确率或稳定合格率也随复杂度下降，才能构成较强的承载能力退化证据。

### 10.5 事实正确性

设标准事实为 `y(k)`，输出抽取值为 `ŷ(k)`，允许误差为 `ε(k)`：

```text
FactAccuracy = Σ[权重 × I(|ŷ(k)-y(k)|≤ε(k))] / Σ权重
```

同时报告：

- 核心事实正确率；
- 字段错位率；
- 无依据断言率；
- 整份输出事实全正确的运行比例；
- 缺失数据擅自补全次数。

观测样本中没有发现错误，只能表述为“本次样本未观察到错误”，不能直接宣称真实正确率为 100%。

### 10.6 跨次稳定性

业务主指标建议采用稳定合格率：

```text
StablePass = 同时满足事实、核心指令和结构门槛的生成次数 / 该组全部生成次数
```

辅助指标包括：

- 同组总分中位数与四分位距；
- 核心规则遗漏项在不同生成间的变化；
- 关键结论翻转率；
- 结构、正式程度、简洁度和客观性的组内标准差；
- 两批实验之间的合格率差异。

不建议只使用文本 embedding 相似度判断稳定性，因为正常措辞变化不等于业务不一致，模型也可能稳定地重复同一个错误。

### 10.7 业务盲评

输出删除组名、Prompt 长度和生成顺序后随机编码。建议由 8—12 名业务评委进行盲评，另设 2 名掌握事实底稿的核验人员。

业务评委只评价：

- 是否愿意直接使用；
- 结构是否清晰；
- 是否具有分析价值；
- 政务表达是否适配；
- 修改到可签发状态预计需要多少分钟；
- 四份中最愿意发给领导的是哪份；
- 最不愿意接手修改的是哪份。

事实正确性主要由程序与专业核验人员判断。若使用 LLM-as-judge，只能作为辅助指标，不能让被测模型自评，也不能把它作为唯一证据。

## 11. 边际效用与成本

在事实硬门禁通过的前提下，使用预先登记的固定业务质量评分 `Q`：

```text
MR(A→B) = (Q(B)-Q(A)) / (Token(B)-Token(A))
```

其余相邻组同理。业务展示时可换算为：

> 每增加 1000 个 Prompt token，带来多少一次可用率或业务质量增量。

完整成本建议包括：

```text
单次总成本 = API成本 + 人工复核成本 + 返工成本 + Prompt维护摊销

每份合格输出成本 = 单次总成本 / StablePass
```

真正需要比较的不是“哪个 Prompt 单次最高分”，而是“哪个 Prompt 生产一份合格输出的平均成本最低”。

## 12. 预先登记的结果判据

以下数值可作为初始建议，最终阈值应由业务方在看到实验结果前确认并锁定：

- A→B 业务质量有实质提升，事实和共享核心要求不劣化：合理增益区；
- B→C 的单位 token 收益不足 A→B 的 25%，且一次可用率或编辑时间无实质改善：边际递减区；
- C 或 D 相对 B，共享核心遵循度下降至少 5 个百分点，或稳定合格率下降至少 10 个百分点：过载证据；
- 稳定合格率低于 50%，或共享核心遵循度相对最佳组下降至少 20 个百分点，并在两个独立批次复现：崩溃风险区；
- 核心事实发生任何错误：该次输出硬门禁失败。

正式统计应同时披露：

- 各组中位数、均值和分布；
- 组间差值；
- 相对风险；
- 效应量；
- 95% 置信区间；
- 多重比较校正后的结果。

单场景的 30 次重复可采用匹配 bootstrap 或相应的配对非参数检验。多数据包正式实验可将组别作为固定效应、数据包作为随机效应，采用混合效应模型。

## 13. 面向业务方的现场展示

### 13.1 展示原则

- 主舞台只显示随机代码 P、Q、R、S；
- 先评分，后揭晓组别；
- 现场生成只承担演示作用；
- 正式结论来自事先封存的完整重复样本；
- 所有样本都纳入统计，不挑选最好或最差的文章。

### 13.2 建议流程

总时长约 45—55 分钟。

1. **说明实验规则，3 分钟**  
   强调实验不预设哪组一定失败，观察的是结果分布而不是单篇文章。

2. **展示事实底板，5 分钟**  
   让业务方先看到唯一事实源、标准事实、缺失值和评分门槛。

3. **四组随机交错生成，8 分钟**  
   每组现场生成 2 份，答案只显示随机代码。

4. **业务方盲评，10 分钟**  
   选择最愿意使用和最不愿意修改的版本，并估计编辑时间。

5. **揭晓完整批次结果，10 分钟**  
   展示每组 30 次封存结果，而不是仅展示现场样本。

6. **展示遗漏热力图和边际收益图，8 分钟**  
   观察 C、D 是否在满足新增微操时开始遗忘共享核心规则。

7. **解释结论边界，5 分钟**  
   只对当前模型、任务和 Prompt 构造负责。

### 13.3 三张核心图

#### 图一：30 次生成结果分布图

- 横轴：A/B/C/D；
- 纵轴：共享核心得分或业务总分；
- 每次生成显示为一个点；
- 绿色：通过事实硬门禁且业务可接受；
- 红色：不可直接交付；
- 同时显示中位数和 95% 置信区间。

该图用于呈现输出分布和“抽到坏答案”的业务概率。

#### 图二：指令遵循热力图

- 行：原子规则；
- 列：每次生成；
- 共享核心规则固定放在顶部；
- 绿色：满足；
- 黄色：部分满足；

#### 图三：Prompt 投入—业务收益图

## 14. 结果解释矩阵

| 实际结果 | 应得结论 |
|---|---|
| A→B 明显改善，C 基本持平，D 下降 | 支持当前场景存在“增益—递减—过载”的局部曲线 |
| B 与 C 质量接近，但 C 成本明显增加 | 已出现边际递减，尚不能称为崩溃 |
| 只有 D-Conflict 下降，D-Clean 稳定 | 主要问题是指令冲突治理，不是 Prompt 长度极限 |
| D-Clean、D-Conflict 都显著下降 | 当前任务存在较强的复杂度过载证据 |
| B-Pad 与 B 稳定，C/D 下降 | 约束密度和交织程度比单纯长度更可能是主因 |
| B-Pad 也明显下降 | 长度、信息位置或注意分配可能是重要因素 |
| 四组全部稳定 | 当前长度和复杂度尚未触及边界，不能人为制造崩溃 |
| C、D 持续改善 | 原假设在当前场景下不成立，复杂约束仍有净收益 |
| 事实始终正确，仅文风规则波动 | 只能称为软约束不稳定，不能称数据能力崩溃 |
| 单次现场结果与 30 次总体分布相反 | 说明不能用一次生成判断模型稳定性 |

## 15. 现场讲解话术

### 开场

> 今天不是比谁更会写 Prompt，也不是证明长 Prompt 一定不好。我们只回答一个经营问题：继续追加要求，是否还能稳定换来可交付价值。

### 展示重复样本时

> 请注意，我们看的是 30 次生成的完整分布。单次好答案不能证明稳定，单次坏答案也不能证明崩溃。

### 如果 B 表现最优

> 从 A 到 B，新增的是高价值、可执行的结构约束，质量得到明显提升；从 B 到 C，Prompt 投入快速增加，但新增规则兑现率和一次可用率没有同步增长。这就是边际递减，而不是模型突然失去能力。

### 如果 D 明显下降

> D 的问题不是字数达到某个神秘阈值，而是大量规则开始争夺同一份注意力和输出空间。模型可能满足了更靠后、更显眼的微规则，却遗漏更重要的核心要求。

### 如果 D 没有下降

> 本轮没有观察到崩溃，说明这个模型在这项任务和当前复杂度内仍有承载余量。严谨的结论是“边界尚未触达”，而不是为了结论继续堆冲突或挑选坏样本。

### 收尾

> Prompt 不存在一个普适的“5000 字崩溃线”。真正需要管理的是：每增加一条要求，是否还能稳定换来可交付价值。Prompt 适合承载任务目标、判断边界和少量高价值约束；大量确定性的格式、校验和流程要求，不应无限堆入一次模型调用。

## 18. 方法依据

本实验设计参考以下公开研究的方法，而不直接沿用其中旧模型的具体分数：

1. [FollowBench: A Multi-level Fine-grained Constraints Following Benchmark for Large Language Models](https://aclanthology.org/2024.acl-long.257/)  
   采用逐级增加原子约束的方式评估复杂指令遵循，说明约束数量比单纯字数更适合作为实验变量。

2. [Instruction-Following Evaluation for Large Language Models（IFEval）](https://arxiv.org/abs/2311.07911)  
   使用可程序验证的指令并区分整份全通过率和单指令满足率，为本实验的 HSR、SSR 和确定性评分提供方法参考。

3. [ComplexBench: A Benchmark for Complex Instruction Following](https://papers.nips.cc/paper_files/paper/2024/hash/f8c24b08b96a08ec7a7a975feea7777e-Abstract-Datasets_and_Benchmarks_Track.html)  
   将复杂度拆分为约束类别、组合方式、嵌套和依赖结构，支持同时记录 token、约束数和组合复杂度。

4. [Lost in the Middle: How Language Models Use Long Contexts](https://aclanthology.org/2024.tacl-1.9/)  
   表明长上下文中的信息利用具有位置效应，因此需要把信息位置视为可能的混杂变量。

5. [IHEval: Evaluating Language Models on Following the Instruction Hierarchy](https://aclanthology.org/2025.naacl-long.425/)  
   对一致与冲突的层级指令进行区分，支持将 D-Clean 与 D-Conflict 分开判读。
