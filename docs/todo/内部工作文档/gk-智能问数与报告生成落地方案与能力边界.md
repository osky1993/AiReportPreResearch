## 一、可行性总判断：取数五要素同构性论证

把 10 个文件里上百条示意 SQL 摊开看，**gk 全部取数只有一个骨架**：

```sql
SELECT SUM(<金额字段>) FROM treasury_income_detail
WHERE stat_date = '<年月>'                -- ② 月份
  AND treasury_code IN (<辖内库集合>)      -- ③ 国库范围
  AND subject_code IN (<科目集合>)         -- ④ 科目集合
  AND budget_level IN (<级次集合>)         -- ⑤ 级次集合（全口径时省略）
```

库存表同构（金额字段换 `balance`、月份换月末日期、无科目/级次维），其余全部差异——同比、环比、占比、差额、排名、子科目下钻——都是**在这个骨架的多次取数结果之上做四则运算或排序**。这与本工程「参数化 MQL 指标模板 + DERIVED 程序派生」模型逐要素对得上：

| # | gk 取数要素 | gk 原文形态 | 本工程对应机制 | 同构性 |
|---|---|---|---|---|
| ① | 金额聚合 | `SUM(current_period_amount / year_to_date_amount / balance)` | `mqlTemplate.metrics` 的 `op:"sum"`，`valueColumn` 一行一值契约 | ✅ 原生支持 |
| ② | 月份 | `stat_date = '202603'`（收入表 varchar6）/ `stat_date='2026-03-31'`（库存表 date） | 占位符 + `PeriodResolver` 程序填充；现有 `{{period_start}}/{{period_end}}`，需扩 `{{period_month}}`（→ 适配点 1） | ✅ 需小改 |
| ③ | 国库范围 | 辖内子查询（一层 OR，市级两层穿透） | `{{treasury_scope}}` 程序查 `treasury_basic_info` 展开为 IN 字面量（→ 适配点 1/2） | ✅ 需小改，且比原方案更优 |
| ④ | 科目集合 | `subject_code IN ('T010101',…)` 固定字面量 | 指标模板内固定字面量——**指标定义即口径**，一个科目集合沉一个指标 | ✅ 原生支持 |
| ⑤ | 级次集合 | `budget_level IN ('4','5')` 固定 / 按 treasury_level 动态 | 固定档位直接写进模板；动态档用 `{{budget_levels}}` 程序解析（→ 适配点 1） | ✅ 需小改 |

**体裁与派生机制的对应**：

| gk 报告需求 | 本工程机制 | 现状 |
|---|---|---|
| 月报体裁 | 模板 `periodTypes: ["MONTH"]`（`treasury-monthly.json` 已在跑） | ✅ Phase03 已支持月/季 |
| 本期同比 / 累计同比（含「上年基数 0 标无同比」） | 指标 `comparable: true`，④FactBuildStep 用同一模板换期间重取后程序算差与幅度，除零规则天然对应「无同比」 | ✅ Phase03 已支持同比 |
| 上月累计 / 环比 | 同上，期间前移一月（【上月累计无定义】销号后启用） | ✅ 机制已有 |
| 差额（其他各项税收、非税） | `derived: {op:"subtract", left, right}` | ✅ 原生支持 |
| 占比（税收÷一般公共预算、土地出让÷地方财力、税种÷税收） | `derived: {op:"divide", left, right}` | ✅ 原生支持 |
| 子科目动态下钻 | `dimensions` 维度指标一段式（→ 适配点 3） | ✅ 机制已有，用法新 |
| 同级排名 | `dimensions` + DERIVED 程序排序（→ 适配点 4） | ⚠️ 需扩 DERIVED 一个 rank 算子 |
| 8 位小数汇总后再算比率 | ④ 程序算派生值（BigDecimal），⑥ 按展示精度替换——精度规范落在 `display_value` 渲染，需对方给展示规范（第二批清单第⑧项） | ✅ 架构吻合，参数待补 |

对照现有资产的目标形态（`src/main/resources/report/metrics.json`）：普通指标如 `cny_total_balance`（固定 filter + sum + valueColumn）、派生指标如 `week_net_inflow_cny`（`derived.subtract` 引两个基础指标）、维度指标如 `week_txn_amount_by_currency`（`groupBy` 多行 + 每行一 fact）——gk 的直取/差额占比/下钻排名三类需求分别落进这三种形态，**不需要发明新的指标类别**。

**结论：可行。** gk 场景是本工程模型的「窄化特例」（单事实表、单聚合算子、五要素全枚举），落地工作量主要在语义资产编写与 4 个引擎适配点，不在架构。前置条件是仲裁文档的口径闭环。

## 二、4 个引擎适配点

所有适配点共同遵守三条底线：**零-LLM（③FetchStep 不引入任何模型调用）、SQL 可复现（同输入同 SQL、sql_hash 稳定）、集合可审计（程序展开的每个集合落 `report_step` I/O 留痕）**。

### 适配点 1：占位符协议扩展——{{period_month}} / {{treasury_scope}} / {{budget_levels}}

**现状**：占位符白名单仅 `{{period_start}}` / `{{period_end}}`（日期），由 `PeriodResolver` 解析、`MqlTemplateFiller` 填充、`TemplateValidator` 的 PLACEHOLDER 校验兜底残留检测。

**扩展三枚，全部程序填充期解析**：

| 占位符 | 语义 | 解析方式 |
|---|---|---|
| `{{period_month}}` | varchar6 年月（'202603'） | `PeriodResolver` 从报告期解析；同比/环比取数时程序做年份/月份前移（'202603'→'202503'/'202602'） |
| `{{treasury_scope}}` | 辖内库集合 IN 字面量 | 填充期只读查 `treasury_basic_info`：本库 OR `admin_treasury_code`=本库；查询库 `treasury_level='3'` 时按原文规则再下钻一层（见适配点 2）。展开结果（完整代码清单）写入 step I/O |
| `{{budget_levels}}` | 级次集合 IN 字面量 | 填充期查询本库 `treasury_level`，按动态规则映射：'3'→('3','4','5')、'4'→('4','5')、'5'→('5')。固定档位（中央'1'/省'2'/市'3'/区县'4'/乡镇'5'、以及全口径不带条件）**不用占位符**，直接写死在指标模板里——档位本身就是口径的一部分 |

**改动落点**：`report/pipeline/PeriodResolver`（月字符串格式与前移）、`MqlTemplateFiller`（新占位符填充 + 集合展开留痕）、新增一个小解析器（如 `TreasuryScopeResolver`，只读查 basic_info）、`TemplateValidator` 的占位符白名单（三处共用一套规则，改这一处）、`MqlParameterizer`（向导反向参数化时识别新占位符）。

**影响面评估**：全部落在报告层辅助类，底座引擎（`ir/Mql.java`、`MqlValidator`、`MqlSqlCompiler`）**零改动**；现有 17 个演示指标不受影响（旧占位符继续有效）。可复现性说明：`{{treasury_scope}}` 展开依赖国库树当时状态，树变更会变 SQL——这不是破坏可复现，而恰是审计要的效果：每次运行用了哪些库，集合字面量在 SQL 与 step 留痕里都看得见。

### 适配点 2：两层穿透嵌套子查询 → 程序展开替代（且更优）

**问题**：市级口径（treasury_level='3'）要求把「孙库」（乡镇库）纳入，原文用两层嵌套子查询（xbiaoge1 L236-237 等 8 个文件文末通用段，xduanluo3 L7-13 更是把它整个塞进收入查询的 IN 条件里）。本工程 MQL 的子查询契约是**子查询自成作用域、不可再嵌套**（`ir/Mql.java`），两层穿透直接超出 IR 表达力。

**方案**：不扩 IR。`{{treasury_scope}}` 的解析器在程序侧做两次只读查询（一层展开 → 结果再展开一层），把最终库集合以 IN 字面量填进模板。

**为什么程序展开反而更优**：
1. 审计友好——嵌套子查询在 SQL 里是黑盒，程序展开后每个入围库代码都是字面量，卡点 1/2 的人和事后审计都能逐库核对；
2. 口径显式——「穿透几层」由程序规则决定并留痕，不依赖 SQL 写对；
3. 复用——同一次运行内多个指标共享同一份展开结果（解析一次，填充 N 处），比每条 SQL 各跑一遍子查询更省。

**改动落点**：与适配点 1 的 `TreasuryScopeResolver` 同一处（递归深度 ≤2，按 treasury_level 决定）。**影响面**：无 IR/编译器改动；`treasury_basic_info` 仅 246 行，展开集合量级无风险。

### 适配点 3：动态子科目下钻 → dimensions 指标一段式

**问题**：xduanluo4/5/7 的子科目取数是两段式——先 `select distinct subject_code … like '<父码>%' and subject_code<>'<父码>'` 发现子科目清单，再逐科目回带查询（原文这些 SQL 均缺 AND/WHERE 连接词，属示意伪代码）。静态模板做不了运行期数据探查。

**方案**：不拆两段，用 dimensions 指标一段式表达——`groupBy: ["subject_code"]` + filter `{"field":"subject_code","op":"like","value":"1010101%"}` + `{"op":"!=","value":"1010101"}`，一条 MQL 直接出「每个子科目一行」，④FactBuildStep 每行落一个 fact（与现有 `week_txn_amount_by_currency` 按币种拆解完全同构）。子科目集合随数据自然变化，事实行数动态，正是 dimensions 契约设计的场景。

**改动落点**：**零框架改动**，纯指标定义工作（涉及 4 个下钻族：国内增值税 1010101%、企业所得税 10104%、个人所得税 10106%、出口退税 1010103%、社保 102%）。注意点：`nullPolicy` 用 ZERO（某月无某子科目属正常）、子科目行的同比要求 FactBuild 对维度值做行对齐（Phase03 维度拆解已有该机制）。

### 适配点 4：排名 → dimensions + DERIVED，不用窗口 rank

**问题**：xduanluo1（库存排名）、xduanluo2（预算收入累计增速排名）、xduanluo3（税收累计增速排名）都是「同级兄弟库（同 admin_treasury_code + 同 treasury_level）逐库算指标后比较名次」。IR 虽支持窗口函数（rank/dense_rank），但这里不用。

**方案**：dimensions 指标 `groupBy: ["treasury_code"]`（范围=同级库集合，程序展开同适配点 1）取出每个兄弟库的指标值，各成一个 fact；名次由 ④FactBuildStep 的 DERIVED 程序算（需给 DERIVED 扩一个 rank 型算子：输入维度事实组 + 目标库，输出名次）。

**不用窗口 rank 的三个理由**：
1. **排名基数往往是 DERIVED 本身**——xduanluo2/3 排的是「累计同比增速」，增速=跨期两次取数的程序派生值，SQL 窗口函数根本拿不到上年同期那次取数的结果，只能程序侧排；
2. **事实可钻取**——每个兄弟库的数值都成 fact 入 `report_fact`，报告正文「列第 X 位」的证据链（各库数值）可在证据钻取页逐个核对；窗口 rank 只返回名次，兄弟库数值不落地；
3. **口径显式可审计**——并列名次规则、降序字段、参与排名的库清单全在程序里明示留痕（顺带规避【排名未参数化】的原文伪代码坑）。

**改动落点**：`FactBuildStep` 的 DERIVED 算子清单 +1（rank）；指标 JSON 的 `derived` 结构扩一种 op。**影响面**：④ 一处，纯程序逻辑可单测（照 `NumberAuditorTest` 范式）。

### 4.2 报告流水线边界

| 维度 | 边界设定 |
|---|---|
| 能进第 4 层的指标范围 | **只进「仲裁后口径」**：科目集合、级次归属、期间算式三要素全部闭环的指标才走 metric-wizard 沉淀（试查 → 人工核验 → `MqlParameterizer` 参数化 → 五重校验 → publish）；🚫 行对应指标在仲裁销号前不建 DRAFT |

### 4.3 明确「不做」清单

| 不做 | 理由 |
|---|---|
| 不做预测（下月收入预估、趋势外推） | 材料无口径依据；本工程定位是「照事实写」，预测数字无 fact 可锚 |
| 不做归因编造（「因 XX 政策导致增长」类因果解释） | ⑤ 的 stylePrompt 只能改文风；增减原因除非对方提供业务归因数据源，否则正文只陈述数字事实 |
| 不做跨口径混算 | 全口径与地方级不相加减；T 码与数字码不混合 IN；收入表（月）与库存表（日）不跨表勾稽——除非仲裁给出明确勾稽关系 |
| 不做自愈重写 | ③ 校验失败不回灌 LLM 修 MQL；子科目发现为空、科目集合失配一律 BLOCKED |
| 不做窗口 rank 进 SQL | 排名程序侧算（第二节适配点 4 的三个理由） |
| 不做 `treasury_balance_monthly` 接入 | 定位澄清前 exclude；澄清后单独评估 |
| 不替对方定口径 | 【非税矛盾】等仲裁项即使「看起来显然是笔误」，也等对方书面/源代码确认后才入库 |

## 六、结语：与 golden-set 评测的衔接

每期指标 publish 后，把**仲裁后口径的期望值**固化进报告评测集（`POST /api/report/eval/run` 的 golden-set 机制）：同一输入（国库代码 × 期间）跑流水线，逐 fact 与期望值比对。这给 gk 接入加上最后一道兜底——

1. **仲裁成果不退化**：口径一旦销号定稿，期望值即静态字面量，未来任何模板/指标/引擎改动导致口径漂移，评测立刻红；
2. **对方修数可感知**：源表历史数据被修（清单已问「修数方式」），复跑评测即暴露差异，触发人工复核而非静默出错报告；
