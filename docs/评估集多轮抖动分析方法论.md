# 底座评估集多轮抖动分析方法论

> **一句话定位**：金标准评估集连跑多轮出现「时过时不过」时的逐例归因方法——核心结论是：只要没有用例**连续**失败，抖动通常不是引擎能力缺口，而是 **LLM 残余非确定性 × 用例良性歧义面**的乘积，可在金标准与语义资产（glossary/few-shot）层面收敛，引擎侧无需改动。
>
> 本文自某业务域评估集（46 例、六轮实测）的归因实践中蒸馏而来，方法与分类域无关；原始逐例分析随该业务域下线一并移除，方法论以本文留存。

---

## 一、现象识别：输出方差 vs 能力缺口

对同一评估集连跑 N 轮（建议 ≥5），先看失败用例的**分布形态**：

- **能力缺口**的形态：同一用例每轮都挂（连续失败）——引擎或语义资产确有缺口，按缺口修复。
- **输出方差**的形态：失败用例轮换出现、每个抖动用例都有通过轮次（单例单轮通过率 90%+）——进入本文的归因流程。

## 二、抖动的两个残余源（temperature=0 也存在）

1. **LLM 服务端非确定性**：temperature=0 依然存在的供应商侧因素（MoE 路由、批处理数值差异等），无法从客户端配置消除。
2. **自我修正路径的分叉放大**：带 max-fix-rounds 自我修正的链路里，第一稿差一点的轮次会走上完全不同的修正轨迹，终稿形态随之分化。

同时要正视评估等价判定的刻意严格性（结果值多重集相等 + 列数相等 + 必要时保序）：任何「业务上同样正确」的输出变体——多带一列、标签写法不同、剔不剔特殊行——都判不等价。**严格性本身有价值（防宽松放水），代价是歧义面大的用例把 LLM 的输出方差如实暴露出来。** 由此推论：抖动集中度与用例的「良性歧义面」大小严格正相关。

## 三、归因三分类

| 类别 | 根因 | 典型形态 |
|---|---|---|
| **A：口径自相矛盾残留** | 语义资产（glossary）建议的口径与金标准参考 SQL 实际口径相反（如「特殊占位行剔不剔」两处说法打架）；且个案修复容易**只对齐个案、不清剿同类** | LLM 听 glossary 的轮次行数/值与参考不一致，判负 |
| **B：等价表示歧义** | 同一语义存在多种合法 SQL 表示，金标准未钉死取哪种：分组键选简称还是代码+简称（列数变）、月份标签 `2026-01` vs 生成列 `202601`（值签名变）、「合计」被展开为分组明细（形态变） | 值可能全对，列数/标签/形态校验挂；schema 注释写得越贴心，LLM「读得认真反而犯错」 |
| **C：实体解析路径歧义** | 同一实体名有两条解析路径（如两张表的同名字段存「简称」与「全称」两种取值风格），选哪条路由 LLM 临场决定 | 走错路的轮次查空/查偏；修复一个方向后注意**镜像方向**的同类残余 |

## 四、收敛动作（按性价比排序）

1. **拿实证坐实归因**：失败 case 留存 `generatedSql` 逐一坐实或排除嫌疑；必要时用 pass@N 看每例通过率分布，再动手修。
2. **清剿 A 类矛盾（治本，收益最大）**：矛盾口径二选一后**全局对齐**——glossary 规则与全部金标准参考同步改，不留个案。最大抖源通常由此消失。
3. **B/C 类钉死金标准问法（微调，不改语义资产）**：问法里显式给出列清单（「列出 X 和 Y 两列」）、标签格式（「格式形如 2026-01」）、聚合形态（「只要一个合计数」）、实体路径（指明按哪张表哪个字段等值）。
4. **评估报告口径升级**：对外汇报准确率用 pass@N（或标注单轮方差）比单轮数字更诚实，也能把「能力缺口」与「输出方差」区分开呈现。

**一句话收束**：多轮全稳的用例说明能力在位；抖动用例几乎总能归入「口径自相矛盾 / 等价表示未钉死 / 实体解析双路径」三个可收敛歧义源——优先清剿 A 类，再微调 B/C 类问法，最后升级汇报口径。
